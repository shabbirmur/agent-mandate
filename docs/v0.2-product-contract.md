# Agent Mandate v0.2 product contract

Status: frozen for implementation on `feat/v0.2-protected-github`.

## Product outcome

Agent Mandate v0.2 protects one real, consequential action end to end:

> An agent may propose creating one exact GitHub issue. A separately authenticated
> user may approve that immutable proposal. The issue may then be created once,
> without exposing a GitHub credential to the model or local MCP client.

The first release is deliberately not a generic HTTP, GraphQL, GitHub, or MCP
proxy. New actions require a reviewed, versioned action profile.

## Trust boundary

Untrusted inputs include prompts, model output, MCP arguments and annotations,
workspace files, shell state, and client-supplied identity, task, action,
audience, resource, risk, schema, and idempotency values.

Trusted inputs are produced by the Agent Mandate service: authenticated subject
and workload mappings, server-minted workflow and idempotency identifiers,
versioned action profiles, resolved provider connection and resource IDs,
policy, approval state, credential minting, execution, and evidence storage.

The model may propose or resume an action. It cannot approve an action, select
trusted authorization metadata, restate an approved envelope during resume, or
receive a provider credential.

## Frozen contracts

`am.action.v1` remains unchanged. Product semantics are versioned separately.

The first profile ID is `github.issue.create.v1`. Its deterministic profile hash
covers its complete trusted manifest and JSON input schema. The profile:

- resolves `owner/repo` to an allowed, immutable numeric GitHub repository ID;
- canonicalizes the resource as `github:repository:<numeric-id>`;
- binds the exact normalized title and body;
- is classified `consequential` and always requires approval;
- permits only GitHub's fixed create-issue endpoint; and
- returns only allowlisted issue fields.

An `am.approval-intent.v1` hash binds the canonical action envelope plus the
profile ID/hash, provider and connection IDs, immutable provider resource ID,
expiry, maximum use count, delegation prohibition, risk class, request ID, and
expected approving principal. A change to any bound field requires a new
approval.

## State machine

The non-blocking agent flow is:

1. `github_create_issue` validates arguments against the trusted profile,
   resolves the selected provider target, persists an immutable approval
   request, and returns `approval_required`, a request ID, a secret resume
   handle, an approval URL, and an expiry.
2. The browser approval page authenticates independently. Possession of the URL
   or resume handle is insufficient to approve. The server verifies principal,
   tenant, anti-CSRF state, expiry, connection state, profile hash, and the full
   approval-intent hash.
3. Approve or deny creates an append-only decision event. The first resume after
   approval idempotently creates one active, one-use mandate linked to the
   request. The bearer grant is held only inside the trusted service and never
   returned through MCP.
4. `agent_mandate_resume` accepts only the opaque resume handle. It executes the
   stored envelope; no provider arguments are accepted again.
5. Concurrent resume atomically reserves at most one provider dispatch. A retry
   returns the existing receipt. Ambiguous dispatch is terminal until bounded
   provider reconciliation proves an outcome; it is never blindly repeated.

Approval states are `pending`, `approved`, `denied`, `expired`, and `cancelled`.
Execution states are `not_started`, `reserved`, `dispatching`, `succeeded`,
`failed`, and `ambiguous`. Use budgets are consumed at reservation and are never
refunded after uncertain dispatch.

## Persistence

Migration `002_product_control_plane` adds:

- `provider_connections` and `provider_connection_resources`, containing only
  provider metadata and secret references, never access tokens or private keys;
- `approval_requests`, containing immutable canonical intent, identity and
  workflow bindings, a hash of the resume handle, state, expiry, mandate link,
  idempotency key, and execution projection; and
- append-only `approval_events` with immutable snapshots.

The existing receipt chain remains authoritative for executions. Each product
mandate links to exactly one approval request with the same envelope hash.

## MCP and installation

The public tools are first-party and narrow:

- `github_create_issue`
- `agent_mandate_status`
- `agent_mandate_resume`
- `agent_mandate_receipt`

Policy denials and ambiguous outcomes are returned as structured, terminal tool
results rather than retryable protocol failures. MCP task identifiers are not
treated as trusted host-conversation identity.

The self-hosted release install surface is one command once an endpoint exists:

```bash
npx -y @agent-mandate/cli@0.2.0 protect github \
  --endpoint https://mandate.example.com/mcp
```

A future managed service may safely supply its own fixed endpoint. Until such a
service is published and verified, the CLI fails closed rather than inventing a
default.

Client configuration contains only an Agent Mandate endpoint or a thin stdio
bridge. Provider credentials must not appear in arguments, environment entries,
config files, logs, receipts, or model-visible results.

## Honest protection status

The CLI reports two distinct states:

- **Mediated:** Agent Mandate constrains its route, but another credential or
  network path may still let the agent mutate GitHub directly.
- **Enforced:** provider credentials are absent from the agent boundary and
  provider-mutation egress is isolated to Agent Mandate in a validated reference
  deployment.

A diagnostic scan can establish `mediated` or find obvious bypasses. It cannot,
by itself, prove `enforced`.

## Release gates

No production-readiness claim is permitted until the exact candidate passes:

- PostgreSQL concurrency, replay, revocation, restart, migration, and tenant
  isolation tests;
- real MCP protocol tests plus live Codex and Claude interoperability;
- real GitHub App installation, selected-repository scoping, reconciliation,
  uninstall/suspension, and credential-leak tests;
- crash injection at reservation, token mint, dispatch, provider commit,
  evidence completion, and MCP response boundaries;
- dependency outage, managed database failover, saturation, and soak gates;
- warm authorization overhead p95 below 50 ms and p99 below 100 ms in a dated,
  in-region environment; and
- an external security review and pilot-owner acceptance.

Hosted deployment, GitHub App registration, public package publication, and
client marketplace/registry listing are external release gates, not facts
established by repository code.
